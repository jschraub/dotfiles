# Quickshell replacement-scope capabilities

_Research date: 2026-11-06. Sources are Quickshell's official v0.3.2 documentation and the source/examples repositories linked by that documentation. “Primitive” means an API/protocol binding that still needs QML policy and UI; it does not mean a ready-made desktop service._

## Executive scope

Quickshell is a QML/Qt shell toolkit. Its official guide directs users to compose a configuration from the type APIs rather than presenting a prebuilt bar, launcher, notification center, lock screen, idle daemon, or wallpaper daemon ([guide](https://quickshell.org/docs/v0.3.2/guide/), [module index](https://quickshell.org/docs/v0.3.2/types/)). It can replace **UI/front-end roles** when a complete configuration is written, but it does not automatically replace the backend daemons or their policy.

| Area | Official primitive | Replacement/audit conclusion |
|---|---|---|
| Wayland bar/panel | `PanelWindow` is an anchored, decorationless window; it maps to `zwlr_layer_shell_v1`, supports per-screen instances, exclusive zones, and keyboard focus ([PanelWindow](https://quickshell.org/docs/v0.3.2/types/Quickshell/PanelWindow), [WlrLayershell](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/WlrLayershell), [Quickshell.screens](https://quickshell.org/docs/v0.3.2/types/Quickshell/Quickshell)) | **Good toolkit replacement for Waybar’s rendering**, not a turnkey bar. Layout, modules, click behavior, workspace integration, styling, lifecycle, and startup must be implemented in QML. |
| Launcher | `DesktopEntries`/`DesktopEntry` index desktop files, expose metadata, and can execute an entry ([DesktopEntry](https://quickshell.org/docs/v0.3.2/types/Quickshell/DesktopEntry)); `PopupWindow` supplies anchored popups ([PopupWindow](https://quickshell.org/docs/v0.3.2/types/Quickshell/PopupWindow)) | **Buildable launcher primitive**, not a ready-made launcher. Filtering/search, keyboard navigation, visibility policy, and invocation UI are application code. `DesktopEntry.execute()` currently ignores terminal mode and field codes, so do not assume complete launcher parity. |
| Menus | `PopupWindow`/QtQuick UI can make arbitrary menus; `QsMenuAnchor`/`QsMenuOpener` and tray menu handles expose platform/DBus menus ([core module index](https://quickshell.org/docs/v0.3.2/types/Quickshell/), [SystemTrayItem](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.SystemTray/SystemTrayItem)) | **Menu primitives only.** Quickshell does not provide a general turnkey application menu, control center, or launcher menu. |
| Notifications vs. swaync | `NotificationServer` implements the Desktop Notifications Specification receiver, tracks notifications, and exposes advertised capability flags ([NotificationServer](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Notifications/NotificationServer)) | **Can be the notification daemon only after the config owns the DBus server and supplies UI/policy.** It is explicitly documented as “types for implementing a notification daemon”; actions, persistence, markup/images, and inline replies are opt-in flags (mostly false), and the `notification` signal requires the config to retain notifications. It is not a drop-in swaync UI/history replacement. |
| Session lock vs. hyprlock | `WlSessionLock` binds `ext_session_lock_v1` and creates one `WlSessionLockSurface` per screen ([WlSessionLock](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/WlSessionLock), [surface](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/WlSessionLockSurface)) | **Security-critical primitive, not a turnkey hyprlock replacement.** The protocol-level security guarantee is strong: if Quickshell dies while locked, a conformant compositor must keep the session covered/inoperable rather than expose it. However, the documented example unlocks with a button; authentication is not automatic. Pair it with `PamContext` and design/test the auth UI and failure policy ([PamContext](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Pam/PamContext), [PAM module guidance](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Pam/)). |
| Idle vs. hypridle | `IdleMonitor` reports compositor idle state through `ext-idle-notify-v1`; `IdleInhibitor` sends `idle-inhibit-unstable-v1` and associates the inhibitor with a window ([IdleMonitor](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/IdleMonitor), [IdleInhibitor](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/IdleInhibitor)) | **Not an idle daemon.** These APIs provide notification/inhibition primitives and require compositor protocol support. They do not constitute Hypridle’s configured listener/action engine (lock, DPMS, suspend, etc.). Keep hypridle unless those policies are deliberately reimplemented and tested in the shell. |
| Wallpaper vs. hyprpaper | `WlrLayershell` can place a custom window on `WlrLayer.Bottom` ([WlrLayershell](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/WlrLayershell)); QtQuick can render an image in that window | **Possible custom static wallpaper UI, not a wallpaper service.** The official module index has no wallpaper/hyprpaper module ([module index](https://quickshell.org/docs/v0.3.2/types/)); there is no documented turnkey wallpaper lifecycle, image reload, multi-output wallpaper policy, or hyprpaper IPC replacement. |
| System tray | Referencing the `SystemTray` singleton starts tracking tray contents; `SystemTrayItem` exposes icon, status, activation, scrolling, and associated menus ([SystemTray](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.SystemTray/SystemTray), [SystemTrayItem](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.SystemTray/SystemTrayItem)) | **Tray protocol/client primitive, not a ready-made tray.** A shell must render the icons, handle placement/overflow, and choose how to display menus. The docs say the implementation roughly conforms to the StatusNotifierItem/freedesktop behavior, not that Quickshell provides a complete tray UI. |
| Polkit authentication | `PolkitAgent` registers a user agent and exposes queued authentication flows; the flow includes PAM prompts, errors, cancellation, and submit ([Polkit overview](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Polkit/), [PolkitAgent](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Polkit/PolkitAgent)) | **Agent backend primitive.** A QML dialog can replace an existing polkit agent only if it is actually registered, presents every request/prompt safely, and handles cancellation/failure. The API does not supply a turnkey dialog or remove the system polkit daemon. The feature was added in v0.3.0 and may depend on how the package was built ([changelog](https://quickshell.org/changelog/)). |
| Network backend | `Quickshell.Networking` exposes network/device/Wi-Fi APIs; official docs state that the only available backend is the NetworkManager D-Bus interface and that both D-Bus and NetworkManager must be running ([Networking module](https://quickshell.org/docs/v0.3.2/types/Quickshell.Networking/)) | **NetworkManager front-end integration, not a network daemon or backend abstraction.** It can drive a custom network menu, but does not replace NetworkManager. Do not infer support for iwd, connman, or another backend from the generic module name. |
| Audio backend | `Quickshell.Services.Pipewire` exposes PipeWire nodes/links, default sink/source selection, and readiness; `PwNodeAudio` exposes volume/mute/channels ([Pipewire](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Pipewire/Pipewire), [PwNodeAudio](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Pipewire/PwNodeAudio)) | **PipeWire control/observation API, not an audio server.** A shell can implement a volume/route mixer and OSD, while PipeWire (and any session manager) remains the backend. The docs do not describe Quickshell as a generic PulseAudio/ALSA backend selector or replacement. |

## Security and lifecycle cautions

- `WlSessionLock.secure` becomes true only after the compositor confirms that all screens are covered. The documented failure behavior—solid color and an inoperable session if the lock process dies—is the protocol safety property; it is not proof that the QML screen authenticates the user ([WlSessionLock](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/WlSessionLock)).
- `PamContext` defaults to the `login` PAM configuration, allows a selected user/config directory, and exposes start/respond/abort/completed. The docs say `PamContext` currently supports only the `auth` type; a lock replacement therefore needs explicit PAM configuration and testing for password, fingerprint, retries, and failure handling ([PamContext](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Pam/PamContext), [PAM module guidance](https://quickshell.org/docs/v0.3.2/types/Quickshell.Services.Pam/)).
- Idle APIs are compositor-dependent: `IdleMonitor` requires `ext-idle-notify-v1`, and `IdleInhibitor` requires `idle-inhibit-unstable-v1`. An implementation should verify Hyprland protocol support rather than treating the QML object’s presence as proof that idle policy is active ([IdleMonitor](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/IdleMonitor), [IdleInhibitor](https://quickshell.org/docs/v0.3.2/types/Quickshell.Wayland/IdleInhibitor)).

## Practical replacement boundary

The defensible near-term scope is **Waybar-like shell UI plus custom launcher/menu, notification presentation, tray, and audio/network controls**, with the existing service backends left in place. A Quickshell lock screen is technically possible but should be treated as a separate security project, not bundled into a cosmetic bar migration. Hypridle, hyprpaper, NetworkManager, PipeWire, and the polkit daemon remain services/backends unless their policies are independently reimplemented and validated; Quickshell’s corresponding APIs do not automatically replace them.
